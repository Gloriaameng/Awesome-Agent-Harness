Agent Harness for Large Language Model Agents: A Survey

TL;DR: Agent behavior is a property of the model–harness–environment configuration, not of the model alone. We define the agent harness, decompose it into six runtime functions (ETCSLV), code 34 systems against first-party evidence, and map how harness effects are evaluated.

Overview

Large language model agents act through a runtime that assembles context, calls the model, routes tools, persists state, enforces policy, and records trajectories. We call this runtime the agent harness and argue that it is a consequential and frequently under-reported co-determinant of observed agent behavior. We therefore analyze results at the level of a model–harness–environment configuration, which also specifies permissions, resource budget, and evaluator.

We decompose the harness into six recurrent responsibilities, H = (E, T, C, S, L, V): execution loop, tool registry, context manager, state store, lifecycle hooks, and evaluation interface. With this framework we code 34 systems against first-party documentation and source code, recording source, version, access date, and confidence for every rating, and examine Claude Code, Codex, DeepSeek Harness, and OpenClaw in depth. We then organize harness evaluation into six areas and distinguish four forms of harness adaptation, from within-run reflection to weight-level co-evolution.

What Is an Agent Harness?

An agent harness is the runtime software between a language model and its environment. It runs the execution loop, assembles context, exposes and governs tools, persists state, and records the evidence an evaluator needs.

Example: fixing a failing test

The model proposes an edit. The harness decides which files and instructions the model sees, exposes edit and shell tools, checks approval, runs the test, and returns the output. If the run is interrupted, the harness must restore enough state to resume without repeating completed actions. A failed run can originate in the model's decision, missing context, an unavailable tool, or the recovery policy; the final answer alone does not distinguish them.

Harness, framework, scaffold, and MCP

Harness
The configured runtime that carries an agent through repeated model calls, actions, state transitions, and completion.
Framework / SDK
Reusable components for building a runtime. A deployed harness combines them with application-specific policies and services.
Scaffold
Prompts and workflow structures that organize model behavior. The term overlaps with harness; the survey makes execution and governance responsibilities explicit.
MCP
A protocol connecting clients to tool and resource providers. The harness still decides how those capabilities enter the execution loop and permission policy.

ETCSLV: Six Runtime Functions of an Agent Harness

ETCSLV names six responsibilities that recur across public harness architectures. It locates where a responsibility is implemented; it is not a maturity score.

E Execution loop
Orders model calls and actions, enforces stopping conditions, and handles retry, delegation, and recovery.
T Tool registry
Defines the actions visible to the model, their argument schemas, routing, result handling, and execution contracts.
C Context manager
Selects and transforms instructions, history, observations, retrieved content, and summaries for each model call.
S State store
Persists conversations, workspaces, checkpoints, memory, and pending operations across turns and restarts.
L Lifecycle hooks
Apply permissions, approvals, credentials, sandboxing, and audit before and after execution steps.
V Evaluation interface
Exposes trajectories, state, outcomes, cost, and configuration metadata to an evaluator.

Origins

Contemporary harnesses combine runtime ideas from three lineages: software test harnesses, interactive environments, and LLM agent architectures.

34 Agent Harness Systems Compared

We code 34 systems against the six ETCSLV functions using first-party documentation and source code. Each rating records its source, version or commit, access date, and confidence. Snapshot: 12 October 2026.

Findings

  • 34 / 34E

    All 34 systems document an execution loop; this follows from the inclusion criteria.

  • 14 · 18 · 2V

    The evaluation interface differentiates systems most: rated Full in 14, Partial in 18, and Unverified in 2.

  • 3 ≠ 1S · V

    A transcript, a resumable session, and a reusable evaluation interface serve different purposes and are rated separately.

Four anchor cases

  • Claude Code

    Product

    Integrates repository exploration, editing, command execution, and delegated subagents into one coding workflow. The case shows how context selection and action approval shape the path from a goal to a tested change.

  • Codex

    Runtime

    Connects model and tool events through an execution loop with persisted rollouts, approval, and sandbox controls. The case centers on recoverable state across client surfaces.

  • DeepSeek Harness

    Plugin

    Exposes runtime components through plugins, profiles, and patches. The case concerns component boundaries and controlled runtime modification.

  • OpenClaw

    Gateway

    Coordinates messaging channels, persistent sessions, and scheduled work through a gateway. The case extends the analysis to identity, state, and authority that persist across interactions.

The four systems place the same function in different layers: product, runtime, plugin, or gateway. A system name therefore does not identify the configuration that produced a result.

How Agent Harnesses Are Evaluated

We organize the evaluation literature into six areas. They combine benchmarks, methods, and platforms, and each answers a different question.

Three evaluation questions

  • Configuration comparison. Which complete configuration performs better under declared conditions?
  • Component study. What changes when one mechanism is altered and the rest is held fixed?
  • Trajectory audit. Do permissions, state transitions, tool results, and completion claims match what happened in the environment?

Reporting a harness result requires the model and runtime versions, task environment, tool and approval settings, budget, and execution record, together with cost, recovery behavior, and policy compliance.

Six evaluation areas

Harness effects

Compare runtime configurations or isolate components with the model and task held fixed.

  • Harness-Bench
  • Beyond the Model
  • LongHarness Bench
  • Harness the Memory
  • WildClawBench

Harness evolution and continual evaluation

Measure adaptation and retention as tools, skills, sessions, or runtime components change. Five further works are compared in the table below.

  • SCLATE
  • VeRO
  • AgentSWE

Lifecycle, security, and audit

Probe permissions, attack effects, recovery, and whether records support independent review.

  • HarnessRisk
  • HarnessSecurity-Bench
  • Hearsay
  • SandboxEscapeBench
  • HarnessAudit-Bench

Long-horizon loops and recovery

Test sustained progress, accumulated obligations, and recovery from partial failure.

  • LoopsBench
  • Long-Horizon-Terminal-Bench
  • SWE-Chain
  • ChainSWE
  • Hell or High Water

Protocol and tool substrate

Separate protocol conformance, tool selection, execution, and verified effects.

  • DynamicMCPBench
  • MCP-Bench
  • MCP-AgentBench
  • MCPAgentBench

Evaluation infrastructure

Provide repeatable runs, interchangeable agents and environments, traces, and graders.

  • AgentCompass
  • Harbor
  • HAL

Task environments such as OSWorld, WebArena, GAIA, and SWE-bench measure configured-system performance. Isolating a harness effect requires additional controls.

Harness evolution: what changes

WorkObject of changeQuestion
SkillOptReusable skill textHow can rollout feedback guide persistent skill edits?
Meta-HarnessExecutable harness codeHow can traces and task scores guide search over runtime implementations?
AutoHarnessTask-specific harness and policy codeHow can environment feedback guide action-validating code?
EvoHarnessBenchTools, skills, and agent configurationsHow are adaptation and retention measured across stages?
TaoLiveModel weights and runtime componentsHow does model training interact with a changing harness?

Open Problems

  • Configuration effects. Measure interactions among model, harness, environment, and policy under matched conditions.
  • State continuity. Test what survives compaction, restart, conflict, revocation, and deletion.
  • Independent evaluation. Link trajectories to environment outcomes and to records outside the agent's control.
  • Bounded evolution. Evaluate versioned harness changes on held-out, out-of-distribution, regression, and safety tasks.
